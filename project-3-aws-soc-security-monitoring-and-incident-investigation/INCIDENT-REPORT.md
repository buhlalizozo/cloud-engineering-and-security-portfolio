### What It Means

A valid login succeeded against an RDS database, but the login pattern broke from the account's established access baseline — GuardDuty flagged this as anomalous rather than a standard authentication event.

This distinction matters: because the login itself **succeeded** rather than failed, this is not evidence of a brute-force attempt. A successful anomalous login is a stronger indicator of potential credential compromise, since it suggests the credentials used were valid but the access pattern (timing, source, or behavior) deviated from normal use.

### Investigation Steps

1. Opened the finding directly in GuardDuty Findings console
2. Reviewed the full finding detail panel, confirming:
   - Finding type, severity, and affected resource
   - Actor details (source IP, ASN, location fields)
   - Action type and login count
3. Confirmed the finding correctly propagated into AWS Security Hub within the expected sync window (~5 minutes)
4. Verified this finding was one of 410 total findings visible in the environment, confirming GuardDuty's continuous monitoring was active and generating findings as expected
5. Confirmed the `Sample: true` flag on the finding, establishing this as GuardDuty's built-in test data rather than a real detected event

---

### Impact Assessment

If this had been a real (non-sample) finding, the potential impact would include:

- Unauthorized access to the RDS database if the credential was compromised
- Possible exposure of data stored in the affected database
- Risk of further lateral movement if the same credential is reused elsewhere in the environment

Because this is confirmed sample data, there was no actual production impact. The value of this investigation was validating that GuardDuty and Security Hub correctly detect and surface this class of finding.

---

### Recommended Response (if this were a real finding)

- Rotate the RDS database credentials immediately
- Restrict the RDS security group to known, expected source IP ranges
- Review AWS CloudTrail for the time window around the login to identify how the credential was used and from where
- Review IAM to identify which identity/role the credential belongs to, and assess whether it has excessive permissions
- Temporarily disable or restrict the identity pending investigation
- Continue monitoring for related GuardDuty findings on the same resource or identity

The finding was successfully generated by GuardDuty and confirmed visible in Security Hub, demonstrating that the detection pipeline between the two services is correctly integrated and operational for this account.
